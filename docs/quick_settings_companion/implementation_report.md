## 3. Root-Cause Bugs Caught & Resolved
1. **Cold-start splash deduplication race (`Pixel_9` emulator):** `_handleCompanionInvocation` initially recorded `invocationId` in `_handledCompanionIds` before dismissing the splash screen, causing cold QS launches to skip `CompanionScreen`. Fixed in [lib/main.dart](../../lib/main.dart) and covered via `showSplashOnLaunch: true`.
2. **`DEVICE_OBSERVED` quote leak on verified Math Makers receipt (`RMX5303` physical device):** `CompanionPolicyResolver.buildExplanation` matched `VerifiedFinding.isVerified` across `deviceObserved` findings, causing undisclosed `Camera` to display `"Mentioned in verified policy text"`. Fixed to require `EvidenceStatus.sourceMatched` + keyword inspection.
3. **Unrelated opening-sentence policy quotation fallback (P1 Hardening):** `ReviewCoordinator.askDeniAboutPermission` previously substituted `snapshotText.split(...).first` when `hasVerifiedPolicy == true` and `verbatimExcerpts.isEmpty`, risking misattribution of an unrelated intro sentence as a quoted clause. Replaced with empty quotation `''`, `EvidenceStatus.unverified`, explicit `Matched Policy Excerpt: None`, honest deterministic fallback copy, and `CompanionDisclosureStatus` state separation. Also removed un-negated `'camera input'` from `PermissionComparator` `disclaimPhrases` after regression testing caught an affirmative `"Camera input is used..."` statement being classified as disclaimed.
4. **Conflated `sourceMatchedCount` metric & `DEVICE_OBSERVED` quotation styling (P1 Hardening):** `PolicyReviewReceipt.sourceMatchedCount` previously counted both `sourceMatched` and `deviceObserved` findings, and cards/sheets styled `DEVICE_OBSERVED` strings in quotation/digest blocks. Separated `isSourceMatched` vs `isDeviceObserved` predicates, kept `sourceMatchedCount` strictly policy-quote-only while preserving `verifiedEvidenceCount`, and separated UI presentation across cards, sheets, receipt rows, and `ReviewResultScreen`.

## 5. Known Limitations
1. Android `UsageStatsManager` reports recent application resume timestamps rather than the active foreground dialog window (`Dialog` / permission prompt UI cannot be read without Accessibility/Overlays, which remain excluded).
2. Enprive cannot determine with 100% certainty which specific permission dialog Android is displaying; users confirm the app and choose from declared manifest permissions or use `"I'm not sure which permission"`.
3. Privacy-policy verification relies on exact previously verified `ReceiptRepository` package matches or user-supplied URLs / pasted text (`CompanionPolicyResolver` never guesses URLs from app names).
4. Debug-build cold-start launches on `RMX5303` take ~5s due to Flutter debug JIT startup; AOT release/profile builds should be signed if distributing for end-user cold-launch benchmarking.
5. Live runtime OS permission dialog (`PermissionController`) overlay testing remains unexecuted on physical devices; see [native_permission_dialog_qa_strategy.md](./native_permission_dialog_qa_strategy.md) for the safe standalone QA helper APK strategy.
